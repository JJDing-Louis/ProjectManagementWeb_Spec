# 變更申請：使用者大頭貼上傳與顯示

- 申請日期：2026-09-27
- 狀態：已核准、功能實作與自動化驗證完成；待人工審查、提交與部署
- 追蹤範圍：Backend、Frontend、Spec 三個獨立儲存庫的 `feature/20260927-user-avatar-upload` 分支
- 實作門檻：使用者已於 2026-09-28 確認本文件，可依本變更單修改功能程式碼、資料庫 Schema 與既有規格

## 1. 需求與已確認決策

1. 只有已登入且 **Email 已驗證**的使用者可以上傳或更換大頭貼。此功能不綁定系統角色或 Function；已驗證的 `Viewer` 也可以使用。
2. 使用者只能修改自己帳號的大頭貼。後端必須以登入身分決定目標帳號，不接受可指定他人的寫入路由或帳號 ID。
3. 輸入格式限 JPG／JPEG、PNG。上傳前提供方形剪裁預覽，確認後的顯示圖固定為 **1080 × 1080 像素**。原圖短邊不足 1080 像素時拒絕上傳，避免放大失真；超過 1080 像素或非方形圖片可在畫面調整剪裁區域。
4. **只保存剪裁後的最終圖片**：在 `Accounts` 資料表新增可為空的圖片二進位欄位，將圖片內容存於 SQL Server。重新上傳時覆寫該欄位的舊值。不保留原圖、舊版圖片，也不另存伺服器檔案或物件儲存空間。
5. 大頭貼顯示於個人設定、側邊導覽及使用者詳情；使用者清單暫不顯示。尚未上傳者沿用姓名首字的預設樣式。
6. 本次不提供刪除大頭貼、還原舊版、原圖下載或管理員代替他人上傳功能。

> 「存於資料庫」代表目前圖片可隨 SQL Server 資料持久保存，**不等同獨立備份**。新圖覆寫後，應用程式不保留舊圖；若日後需要災難復原或舊版還原，須另外規劃資料庫備份／還原策略，並由使用者另行確認。

## 2. 現況與影響範圍

- Backend 採 ASP.NET Core Controller、Identity 與 SQL Server。現有 `GET/PUT /api/v1/users/me/profile` 只處理名稱與電話；`Accounts` 沒有大頭貼欄位，也沒有圖片上傳或讀取端點。
- Frontend 採 Vue 3。個人設定只有名稱、電話與偏好；側邊導覽以姓名首字顯示頭像，使用者詳情未顯示圖片。
- Spec 的 User Story、個人資料流程與 Schema 目前把 `Viewer` 可修改的本人資料限定為名稱、電話；需增列「Email 已驗證者可修改本人圖片」這項例外，保留未驗證者仍可修改名稱與電話的既有行為。
- 三個儲存庫目前都在 `feature/20260927-user-avatar-upload`；建立本變更單時工作目錄沒有既有未提交變更。

## 3. 修改方案

### 3.1 Backend 與資料庫

1. 在 `Accounts` 增加 `AvatarImage varbinary(max) NULL`，以 EF Core migration 版本化。此欄位只放最終 1080 × 1080 圖片的位元組，不存 URL、檔案路徑、原圖或 Base64 字串。
2. 新增本人上傳端點（規劃為 `PUT /api/v1/users/me/avatar`，`multipart/form-data`）。在處理圖片前由後端查詢本人帳號目前的 `EmailConfirmed` 狀態；未登入回 401，未驗證回 403，格式或尺寸不符回明確錯誤。既有名稱／電話更新端點不受此限制。
3. 即使前端已完成剪裁，後端仍要限制 request 大小與解碼後像素量、驗證實際 JPG／PNG 內容、拒絕損壞檔案，並重新編碼為受支援的最終格式。不要信任檔名、副檔名、宣告的 MIME 類型或前端回報的尺寸；不保留原圖內的 EXIF 等附加資訊。
4. 只在圖片驗證與處理成功後覆寫資料庫欄位；失敗時保留原有圖片。新增必要的稽核紀錄，但不記錄圖片位元組或個資內容。
5. 新增圖片讀取端點（規劃為 `GET /api/v1/users/{id}/avatar`）：本人可讀取自己的圖片；讀取他人圖片時沿用既有使用者詳情的可見範圍。回傳圖片位元組及正確 Content-Type；沒有圖片時讓前端顯示預設頭像。圖片不放進個人資料或使用者清單的 JSON 回應。
6. 檢查現有 Identity、登入及帳號查詢是否因 `Accounts` 的二進位欄位載入大圖；對不需要圖片的查詢採最小欄位投影或其他局部處理，並以測試確認沒有明顯回歸。

### 3.2 Frontend

1. 個人設定增加檔案選擇、方形剪裁、縮放／定位、1080 × 1080 結果預覽及確認上傳。圖片確認前不呼叫上傳 API；取消不更動既有圖片。
2. 依目前使用者的 Email 驗證狀態控制入口並說明原因；後端仍是最終授權判斷。清楚呈現不支援格式、尺寸不足、上傳失敗與重試狀態。
3. 透過既有 HTTP service 送出圖片，使用具身分驗證的請求讀取圖片；成功後更新個人設定、側邊導覽及使用者詳情的顯示，避免瀏覽器沿用舊圖片快取。保留沒有圖片時的姓名首字備援。
4. 剪裁操作需兼顧手機尺寸、鍵盤可操作性與圖片方向。若需要第三方剪裁／編碼套件，實作前評估授權、維護狀態、套件大小與替代方案。

### 3.3 規格同步與交付

1. 更新 `UserStory.md`、`Flowchart/管理個人資料與偏好.md`、`Schema.md` 及相關測試案例，使驗收條件與 API、資料保存語意一致。
2. 保持既有個人資料 API 的名稱／電話契約可用，不藉此改動帳號、Email、角色或其他業務資料。
3. 依三個儲存庫各自的 GitFlow 規範準備變更與 PR 說明；本變更單不授權自動合併、部署或發佈。

## 4. 驗收與驗證計劃

- 授權：未登入不可上傳；Email 未驗證者不可上傳；已驗證 `Viewer` 可上傳；無法藉由路由或 request 修改他人圖片。
- 圖片：接受有效 JPG／JPEG、PNG；拒絕偽造格式、損壞圖片、短邊不足 1080 及超出安全上限的檔案；最終顯示圖為 1080 × 1080。重新上傳後讀到新圖，失敗時舊圖不變。
- 顯示：個人設定、側邊導覽及使用者詳情顯示新圖；未上傳時顯示預設頭像；重新整理與重新登入後仍可讀取圖片，使用者清單不額外載入圖片。
- 測試：執行 Backend build、單元與整合測試；Frontend lint、型別檢查、單元測試與 build；實際檢查桌面／手機的剪裁、上傳與顯示流程。若整合測試所需 SQL Server 不可用，須明確標示未驗證，不能把略過測試視為通過。

## 5. 風險、取捨與不在本次範圍的事項

| 風險／取捨 | 處理方式 |
| --- | --- |
| `Accounts` 大圖欄位可能增加登入、帳號查詢及 SQL 備份的 I/O 與容量 | 限制輸入及最終檔案大小；避免清單 JSON 與不必要查詢載入圖片；驗證常用流程的資料讀取量。若此方案造成不可接受的效能問題，先回報並確認是否改為一對一圖片資料表。 |
| 前端剪裁可被略過，惡意圖片可能消耗伺服器記憶體 | 後端獨立檢查位元組長度、實際格式、尺寸與解碼上限，重新編碼後才寫入資料庫。 |
| 覆寫後無應用程式層級的舊版可還原 | 明確接受只保存目前圖片；需要可還原備份時，另行制定 SQL Server 備份／還原程序。 |
| 圖片為個人資料，若直接提供公開靜態 URL 可能越權讀取 | 經登入驗證的讀取端點，沿用本人／使用者詳情的資料可見規則。 |
| 多分頁同時上傳可能互相覆寫 | 訂定最後一次成功寫入為目前圖片的行為，並測試並行與失敗情境。 |
